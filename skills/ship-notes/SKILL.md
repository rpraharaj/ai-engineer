# Ship notes

Describe **what actually shipped**. Source of truth is the commit range (and the diff if the messages are vague). Do not invent features, metrics, or migrations.

Read `AGENTS.md` if present.

## Range

Default: since the last version tag (`git describe --tags --abbrev=0` if tags exist) to `HEAD`. If the user named a tag, PR, or date, use that.

```sh
git log --oneline <from>..HEAD
git diff --stat <from>..HEAD
```

If this is not a git repo or the range is empty, stop.

## Detect the format

Use the first that exists and already has entries:

1. `CHANGELOG.md` / `CHANGES.md` / `HISTORY.md`
2. `changelog/` fragments (keep a changelog, towncrier, or this repo's equivalent)
3. GitHub/GitLab release body style if that is what the user asked for and no file exists
4. Otherwise write Keep a Changelog-style sections in the reply only: Added / Changed / Fixed / Removed / Security / Migration

Match heading level, date style, and version prefix (`v1.2.3` vs `1.2.3`) from the last entry. Do not switch the file to a new format.

Version number: from the user's ask, or from this repo's version field (`package.json`, `pyproject.toml`, `Cargo.toml`, `VERSION`, latest tag). If you cannot tell, ask or use `Unreleased`.

## Write

- User-facing first. Group by kind, not by commit hash.
- One line per change. Merge "fix typo" and chore-only commits into nothing, or a single Internal line if this repo records those.
- Call out **breaking** changes and **migrations** the operator must run. Those come from `data-change` plans and the diff, not from guesswork.
- Do not mention agents, models, or "generated by."
- Do not claim performance or security wins unless the commits or a measured `performance` / `security-pass` note say so.

If the repo uses fragments, add one fragment per user-facing change in that tool's naming scheme. Do not also rewrite the rolled-up file unless the user asked to cut a release.

## Optional version bump

Only if the user asked to bump:

- Follow this repo's versioning (semver if that is what tags look like: breaking → major, feature → minor, fix → patch)
- Change the one version file this repo already uses, plus the changelog heading
- Do not tag or publish unless the user asked

## Done

1. Range (`from` → `HEAD`)
2. Path edited or the notes in the reply
3. Breaking / migration callouts
4. Whether you bumped a version (and to what)

Do not commit, tag, or publish unless asked. Next is usually `commit` (notes only or notes + bump). If they asked to tag, publish, or deploy, continue with `cut-release`.
